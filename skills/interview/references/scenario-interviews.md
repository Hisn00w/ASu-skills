# 场景题与系统设计题

用户被要求设计 Agent Demo、内部工具、端侧应用、业务 Case 或系统方案时读取本文件。

## 通用回答骨架

引导用户按以下关系回答，不强迫逐条报标题：

```text
目标用户与业务结果
  ↓
最小范围与明确不做什么
  ↓
输入输出和成功标准
  ↓
工作流、模型、工具和状态
  ↓
权限、失败处理与人工接管
  ↓
可观测性与评测集
  ↓
交付计划和验收门禁
```

## 场景澄清

优先确认：

1. Agent 只提供建议，还是会执行真实操作？
2. 最严重的错误是什么，是否需要一票否决？
3. 正确答案来自确定性规则、业务系统、专家还是人工标注？
4. 有哪些现有 API、数据、设备或部署约束？
5. Demo 的时间、展示对象和验收方式是什么？

陌生行业中，不要求用户假装懂业务规则。好的回答应说明如何让领域专家提供真值，再将其转成版本化、可执行、可回归的验收条件。

## 两周Demo

检查用户是否做到：

- 选一个真实闭环，而不是搭建通用大平台；
- 第一周打通端到端，第二周补失败路径、评测、文档和演示；
- 外部依赖未就绪时先 Mock；
- 高风险写操作先保持只读或加入人工确认；
- 每天保留可运行版本；
- 明确不做复杂多 Agent、全量平台适配或与验收无关的 UI。

可追问：

- 为什么这个范围两周能完成？
- 哪个依赖最可能阻塞，如何降级？
- 如何证明不是只能演示一次的 happy path？
- 如果只剩一周，删掉什么？

## Agent架构判断

检查方案是否把所有逻辑都交给 LLM。确定性计算、权限、金额、数据库约束和设备安全边界应优先使用代码或专业系统；模型适合语义理解、信息抽取、候选规划和非结构化内容处理。

工具应有单一职责、结构化参数和稳定返回；有副作用的工具还应考虑权限、幂等、确认、审计和恢复。

## 验收

至少覆盖：

- 核心任务是否完成；
- 结构化输出和工具参数是否正确；
- 无证据、缺参数和外部失败时是否安全处理；
- 正常、边界、异常和必要的对抗用例；
- 模型、Prompt、工具轨迹、时延和成本是否可观测；
- 高风险错误是否设置阻断门禁。

不要只用“Demo 能跑”“回答看起来不错”作为验收结果。
