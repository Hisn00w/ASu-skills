# 贡献交付与面试准备

在原有贡献流程中增加过程讲解，在本次流程结束时按“原有结果 → 贡献事实卡 → 面试准备”输出。目的在于帮助用户理解本次贡献；原有项目筛选、实现、验证、PR 确认、状态跟踪和求职交接保持原有顺序。每个 PR 单独整理，链接、事实和状态不跨项目混用。

## 1. 流程内容：What / Why / How

随着分析、修改和验证推进，说明已经确认的事实。准备阶段用“拟修改”，完成后用“实际修改”，避免将计划描述成结果。

| 内容 | 向用户说明什么 | 依据 |
| --- | --- | --- |
| What：仓库是什么 | 项目面向谁、解决什么问题、主要用途；本次涉及哪个模块及其作用 | 仓库 README、相关文档和代码链接 |
| Why：为什么选它 | 哪条 Issue 或实际问题值得处理；如何符合用户提示中的岗位、语言、框架或指定方向；为何适合本次贡献 | 用户目标、Issue/问题来源、维护和贡献规则检查 |
| How：原来为什么不行 | 预期与实际行为、触发条件、复现步骤、根因所在文件或逻辑；文档问题则解释原内容为何错误或影响使用 | 复现结果、相关代码/文档、测试证据 |
| How：如何修复 | 修改哪些文件和逻辑、为什么采用此方案、有哪些实际可行的备选及取舍、影响哪些场景 | 实际 diff、提交或文件链接 |
| How：用到什么技术 | 具体语言、框架、库、机制或工具在定位、修复和验证中分别起什么作用 | 本次实际使用情况；区分仓库整体技术与本次改动涉及的技术 |
| How：如何证明 | 实际验证命令、结果证明的行为、未覆盖场景及剩余限制 | 测试、lint、构建、链接检查等实际输出 |
| 协作与状态 | 用户和 Agent 分别做了什么；PR、CI、review、合并的当前状态 | 本次交互、PR 页面、checks 和 review 链接 |

选择理由须具体，例如“用户指定 Java 后端方向，这条 Issue 位于该 Java 项目的请求参数校验模块，且当前代码仍可复现”，而不是只写“项目热门”。用户直接指定仓库时如实说明，不补造岗位匹配理由。

讲修复时把现象、原因、改动和验证连起来。纯文档、链接或格式贡献按真实内容解释，不强行引入代码架构。只有确实存在可行备选时才比较；没有复现或根因证据时说明未确认部分，不为了填满结构猜测。

## 2. 流程结束后：贡献事实卡

把前面已经完成的过程总结成卡片，保留原有结果和求职交接。使用以下字段，未知信息标“待确认”，尚未发生的步骤写“尚未发生”：

```markdown
## 贡献事实卡

- 仓库与链接：
- 仓库用途 / 本次涉及模块：
- 选择理由 / 与用户目标的关系：
- Issue 链接 / 问题来源：
- PR 链接：
- 问题现象、预期行为与复现：
- 根因与证据：
- 实际修改 / 文件、diff 或提交链接：
- 采用方案与取舍：
- 本次用到的语言、框架、机制或工具及作用：
- 验证命令、结果及未覆盖范围：
- 用户实际参与 / 确认范围：
- Agent 实际完成范围：
- PR 当前状态：
- CI 状态与检查链接：
- review 状态与讨论链接：
- 合并状态 / 合并时间（如已合并）：
- 状态核验时间：
- 待处理事项：
- 面试练习记录：见下方题目与回答情况。
```

卡片保留真实 Issue、PR、提交及检查链接；没有 Issue 时记录实际问题来源，尚未创建 PR 时写“尚未提交，无 PR 链接”，不生成虚构链接。CI 未触发、尚无 review 或状态未查询时按实际情况标注，不写成通过或认可。状态变化后更新对应字段，并保留核验时间。

用户只确认目标或方案时就写该范围；Agent 完成的分析、实现和验证记录在 Agent 一栏，不转换为用户亲自完成的经历。未合并、已关闭和已合并按页面实际状态记录；合并不自动证明具体采用范围。

## 3. 面试准备：根据本次 PR 出题并讲解

默认输出 4—6 道贴近本次贡献的练习题，根据实际改动选题，问题中使用本次模块、行为、文件或验证场景。问题帮助用户巩固理解，无需先回答才能完成原有贡献流程。用户要求继续练习时，再针对实际回答追问并记录反馈。

优先从以下方向选择：

1. 这个仓库解决什么问题？本次改动的模块在其中起什么作用？
2. 为什么选择这个 Issue 或问题？它与贡献目标有什么关系？
3. 原来的实现在哪个条件下不符合预期？怎样复现和定位到根因？
4. 实际改了哪些逻辑？为什么采用这个方案？确有其他可行方案时，取舍是什么？
5. 本次用到的语言、框架或机制起了什么作用？修改可能影响哪些场景？
6. 哪项验证能证明修复有效？它为什么能发现原问题，还有哪些范围没有覆盖？
7. 用户具体参与或确认了什么，Agent 完成了什么？有实际 review 时，维护者反馈如何影响修改？

以上是选题方向，输出时替换成与本次 PR 有关的具体问题。事实较少的文档贡献可以少出题，不为了凑数量扩展成无关原理题。没有 review、CI 失败或合并记录时，不预设这些事情发生。

每题按以下方式输出：

```markdown
### 题目 1：围绕本次具体改动的问题

- 事实依据：对应 Issue、文件、diff、验证结果或协作记录。
- 回答要点与讲解：解释应当讲清的因果关系、技术细节或方案取舍。
- 进一步追问：基于本次事实继续检查理解的问题。
- 用户回答情况：未练习 / 用户实际回答摘要。
- 待巩固内容：尚未回答时注明待练习确认；回答后记录实际遗漏。
```

回答要点可以解释 Agent 已完成的工作，让用户学习原理与过程；涉及“你亲自做了什么”时，只使用用户实际参与范围，不生成冒充亲自实现的第一人称经历。未回答不等于不理解，也不能记为已掌握。用户回答后，将回答摘要及待巩固内容更新到事实卡关联的练习记录。

例如，本次事实确实是“补上请求参数的边界校验并添加对应测试”时，可以问“此前哪类输入绕过了校验？新测试如何证明该输入现在被拒绝？”；本次只是修复文档链接时，则问“原链接为什么失效？怎样确认新地址指向相同内容？检查覆盖了哪些引用？”这些是出题示例，不是本次已发生的贡献。

## 公开面经参考（按需）

保留[开源贡献面经案例](interview-examples.md)中的来源链接。用户需要公开案例，或已有案例有助于解释本次追问时，再读取相应案例并核对所选原帖的相关完整正文。公开案例属于来源作者，不作为用户贡献事实，也不作为生成本次练习题的前置条件。

公开原帖的问题标为“原帖明确记录”，根据当前 PR 生成的问题标为“基于本次贡献生成”。无法读取正文或没有对应案例时说明情况，继续根据本次实际改动提供练习；不从标题、录用结果或摘要补造面试过程。
