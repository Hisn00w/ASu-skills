# /job-match：岗位匹配分析

把招聘 JD 拆成可核验的要求，再与用户已有证据逐项对照。目标不是生成一个看似精确的匹配分数，而是帮助用户判断：哪些要求已经有证据、哪些只是简历没写清、哪些确实需要补足，以及是否值得投入一次申请。

## 输入

优先读取当前对话已有材料，不要求用户重复提供：

1. 一个明确的目标 JD；
2. 当前简历、经历说明或主张—证据账本；
3. 可选的求职偏好，例如地点、薪资、岗位级别、行业和不可妥协条件。

没有完整 JD 时，可以基于用户提供的岗位截图、链接或文字片段分析，但必须标明信息边界。只有职位名称、没有岗位要求时，先请求 JD，不根据职位名称猜测具体门槛。

## 分析方法

1. 从 JD 提取岗位职责、硬性条件、核心能力、加分项和申请约束；合并重复表述，不把公司宣传语当作候选人要求。
2. 为每项要求寻找用户材料中的直接证据，记录证据位置和个人边界。团队成果不能自动视为个人能力。
3. 将匹配状态限定为：
   - `已匹配`：存在明确、可展开的事实或作品证据；
   - `表达缺口`：用户做过相关工作，但简历或材料没有清楚呈现；
   - `证据不足`：材料暗示可能具备，但无法支撑对外表述；
   - `真实缺口`：现有事实明确不满足或用户确认尚未具备；
   - `待确认`：缺少决定性信息，不能替用户猜测。
4. 先判断硬性条件，再评估核心职责与加分项。地点、学历、工作授权、年限或必备证书等门槛应单独展示，不被其他优势抵消。
5. 给出 `建议投递`、`补充材料后投递`、`谨慎投递` 或 `暂不建议投递`，并列出促成结论的关键证据。不要输出伪精确的百分比匹配分数。

## 默认交付

按以下结构输出：

1. **岗位结论**：一句话说明建议和最关键原因；
2. **要求—证据矩阵**：JD 要求、重要性、用户证据、匹配状态、风险或下一步；
3. **硬性门槛**：逐项列出已满足、未满足和待确认项；
4. **优先补强**：最多 5 项，区分“调整表达”“补证据”和“补能力”；
5. **投递策略**：是否建议投递、适合使用的简历版本以及需要确认的问题；
6. **后续交接**：仅在用户需要时生成对应的下一步提示。

矩阵中的“用户证据”必须能回指简历段落、项目、作品、PR、文件或用户明确陈述。找不到证据时写“未提供”，不能用常识补齐。

## 路由与交接

- 需要改写简历 bullet、摘要或 HR 开场白：把矩阵中的 `表达缺口` 和已确认事实交给 `/great-resume`；
- 需要生成或编辑 HTML/PDF 简历：交给 `/make-resume`；
- 需要预测问题或模拟面试：把高风险要求和 `证据不足` 项交给 `/interview`；
- 已决定申请并需要填写网页：把已确认字段交给 `/job-apply`；
- 需要记录申请状态：交给 `/offer`。

分析本身不授权修改简历文件、填写申请、发送消息或提交投递。用户只问“匹不匹配”时，到投递建议为止。

## 事实边界

- 不为了贴合 JD 添加用户没有做过的技能、职责、职级、项目或指标；
- 不把相邻技术自动视为掌握，例如会 React 不等于具备 Vue 项目经验；可以说明可迁移性，但状态仍按证据判断；
- 不把“优先、熟悉、了解”统一解释为硬性要求，结合 JD 原文和职责上下文判断；
- 不因单个关键词缺失直接否定岗位，也不因关键词重合就判断胜任；
- 涉及时效性条件或外部职位页面时，保留抓取日期，页面失效后标记为待重新确认。
